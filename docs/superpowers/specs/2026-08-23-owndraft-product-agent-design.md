# OwnDraft — MABC 2026 제품·에이전트 설계 명세서

> **가칭:** OwnDraft  
> **한 줄 정의:** AI 초안을 사용자의 실제 생각과 문체로 되돌리는, 사실 보존형 개인 글쓰기 편집 에이전트  
> **문서 상태:** 사용자 승인 완료 — 구현 계획의 기준 문서  
> **작성일:** 2026-08-23  
> **대상 대회:** Making AI Beneficial Challenge 2026  
> **핵심 원칙:** AI 흔적을 속여 숨기는 것이 아니라, 사용자의 기여를 늘리고 글의 출처·변경 과정을 투명하게 만든다.

---

## 0. 이 문서에서 확정하는 것

이 문서는 OwnDraft의 제품 방향, 예선용 단일 스킬, 결선용 서비스 MVP, 에이전트 구조, 데이터 흐름, 안전 기준, 평가 방법, 개발 범위를 하나의 기준으로 고정한다.

이 문서는 사용자 승인을 받았으며, 실제 프롬프트·코드·데이터베이스·UI 구현은 함께 제공되는 STAGE 1·STAGE 2 구현 계획을 기준으로 진행한다.

### 이번 설계에서 확정한 핵심 결정

1. **“AI 워터마크 제거기”는 만들지 않는다.**
   - Claude와 Gemini의 텍스트 워터마크는 숨은 문자나 파일 메타데이터를 지우는 문제가 아니다.
   - 단어·토큰 선택 과정에 통계적인 패턴을 남기는 방식이므로, 제품이 “완전 제거”를 보장할 수 없다.
   - 탐지 우회 자체를 제품 목표로 삼으면 기술적으로 불안정하고, 평가·윤리·브랜드 측면에서도 불리하다.

2. **제품의 중심은 ‘개인 문체 복원’이다.**
   - AI가 만든 초안을 단순히 패러프레이징하지 않는다.
   - 사용자가 실제로 하고 싶은 말, 경험, 판단, 근거를 먼저 확보한 뒤 그 사람의 문체로 편집한다.

3. **사실 보존이 문체 변환보다 우선한다.**
   - 이름, 숫자, 날짜, 인용, 출처, 사건 순서, 사용자 경험은 `Claim Locker`가 잠근다.
   - 근거가 없는 새 사실은 생성하지 않는다.

4. **예선과 결선을 분리한다.**
   - 예선은 타임리 AI에서 구현 가능한 **단일 기능 중심 스킬**로 완성한다.
   - 결선은 개인 문체 메모리, 문장별 Diff, 승인 학습, 검증 대시보드를 갖춘 서비스 MVP로 확장한다.

5. **가칭은 `OwnDraft`를 사용한다.**
   - 앞서 고려한 `VoiceProof`는 현재 음성 신원 보호 서비스가 이미 사용 중이므로 혼동을 피한다.
   - 최종 브랜드명은 결선 진출 후 상표·도메인 검토를 거쳐 결정한다.

# 1. 문제 정의

## 1.1 사용자가 실제로 겪는 문제

AI로 글을 작성하면 초안을 빠르게 만들 수 있지만, 결과물에는 자주 다음 문제가 생긴다.

- 문장은 매끄럽지만 사용자가 실제로 한 말처럼 보이지 않는다.
- “빠르게 변화하는 시대”, “단순한 도구를 넘어”, “결론적으로” 같은 상투 표현이 반복된다.
- 구체적인 경험이나 판단이 빠지고 누구에게나 적용되는 추상적인 문장만 남는다.
- 숫자, 날짜, 출처, 고유명사를 다듬는 과정에서 뜻이 변하거나 사실이 추가될 수 있다.
- 사용자는 AI 초안을 받은 뒤 다시 읽고, 자신의 말투로 고치고, 사실을 확인하는 일을 매번 반복한다.
- 일반적인 Humanizer는 문장을 자연스럽게 바꾸지만, 사용자의 실제 생각을 수집하고 사실을 잠그는 과정은 약하다.
- AI 탐지기 점수만 낮추는 서비스는 글의 품질·사실성·저자성을 보장하지 못한다.

즉, 문제는 “AI가 쓴 티” 하나가 아니다.

> **AI 초안이 사용자의 생각, 경험, 표현 습관을 충분히 담지 못하고, 사용자가 이를 매번 수작업으로 복원해야 한다는 것이 본질적인 문제다.**

## 1.2 현재 사용자가 하는 수작업

1. AI에게 글 초안을 요청한다.
2. 너무 거창한 서론을 지운다.
3. 반복되는 표현을 바꾼다.
4. 자신이 실제로 겪은 사례를 끼워 넣는다.
5. 숫자와 출처가 맞는지 다시 확인한다.
6. 말투를 본인처럼 바꾼다.
7. 문장별로 여러 번 다시 수정한다.
8. 다음 글에서도 같은 일을 반복한다.

OwnDraft는 이 반복 과정을 하나의 설명 가능한 편집 흐름으로 만든다.

# 2. 제품 비전

## 2.1 비전 문장

> **AI 때문에 사라진 사용자의 생각과 말투를 되찾는다.**

## 2.2 제품 정의

OwnDraft는 AI 초안, 사용자의 문체 샘플, 글의 목적과 독자, 사용자가 직접 제공한 경험과 근거를 함께 분석해 다음을 수행하는 개인 글쓰기 편집 에이전트다.

- AI 특유의 상투적인 글쓰기 패턴 진단
- 사실·주장·경험 추출 및 잠금
- 부족한 사용자 맥락을 질문으로 수집
- 사용자의 문장 리듬과 표현 습관을 반영한 재작성
- 원문과 수정문의 차이 및 수정 이유 제공
- 사용자가 승인한 수정만 개인 문체 프로필에 반영

## 2.3 제품이 하지 않는 일

- Claude·Gemini·Turnitin·GPTZero 등의 탐지를 “100% 우회”한다고 주장하지 않는다.
- 텍스트 워터마크를 제거했다고 판정하거나 보증하지 않는다.
- 특정 탐지기 점수가 낮아질 때까지 무한히 문장을 바꾸지 않는다.
- 사용자가 제공하지 않은 경험, 통계, 출처, 인용문을 만들어내지 않는다.
- 타인의 고유한 문체를 무단 복제하는 도구로 사용하지 않는다.
- 사용자의 승인 없이 문체 샘플을 학습 데이터로 사용하지 않는다.
- 예선에서 너무 많은 기능을 억지로 합치지 않는다.

# 3. 대상 사용자와 핵심 사용 상황

## 3.1 우선 대상 사용자

### 1순위: AI 초안을 자주 다듬는 개인 창작자

- 블로그 작성자
- 뉴스레터 운영자
- SNS 콘텐츠 제작자
- 1인 사업자
- 개인 브랜딩을 하는 취업 준비생과 대학생

이들은 글을 자주 만들고, 자신의 말투가 중요한 사용자다. 전후 비교와 효과를 데모하기 쉽다.

### 2순위: 반복적인 실무 글을 작성하는 직장인

- 업무 메일
- 보고서
- 제안서
- 회의 후 공유 글
- 사내 공지

이들은 사실 보존과 문체 일관성이 중요하다.

### 3순위: 팀·브랜드 문체를 관리하는 조직

- 마케팅 팀
- 고객지원 팀
- 스타트업 콘텐츠 팀
- 대행사

결선 이후 확장 대상이다. 예선·초기 MVP에서는 우선순위가 낮다.

## 3.2 핵심 Job To Be Done

> “AI로 만든 초안을 매번 처음부터 다시 고치지 않고, 사실은 그대로 유지하면서 실제 내가 쓴 글처럼 빠르게 완성하고 싶다.”

## 3.3 대표 사용 시나리오

### 시나리오 A — 블로그 글

사용자가 AI로 만든 블로그 초안과 자신이 직접 쓴 글 2~3개를 넣는다. OwnDraft는 상투적인 문장을 표시하고, 실제 경험이 필요한 부분을 최대 세 가지 질문으로 확인한 뒤 사용자 말투에 맞춘 글을 제안한다.

### 시나리오 B — 업무 메일

사용자가 거친 메모와 AI가 만든 정중한 메일을 입력한다. OwnDraft는 날짜, 일정, 금액, 담당자를 잠그고, 회사 문체에 맞게 짧고 명확한 메일로 바꾼다.

### 시나리오 C — 공모전 소개 글

사용자가 서비스 설명 초안을 입력한다. OwnDraft는 과장 표현과 모호한 효과를 줄이고, 실제 문제·사용자·입출력·검증 결과가 드러나도록 바꾼다.

# 4. 경쟁 기준과 차별화

## 4.1 기준선: 오픈소스 Humanizer

`blader/humanizer`는 현재 위키피디아의 “Signs of AI writing”을 기반으로 35개 패턴을 사용한다. 글의 의미를 바꾸지 않고 AI처럼 보이는 표현을 다듬으며, 사용자가 글 샘플을 주면 리듬·단어 선택·문장부호 습관을 따라간다.

OwnDraft는 이 접근을 참고하되 그대로 복제하지 않는다.

## 4.2 OwnDraft의 차별점

| 구분 | 일반 Humanizer | OwnDraft |
|---|---|---|
| 패턴 제거 | 있음 | 있음, 한국어 전용 패턴 강화 |
| 개인 문체 반영 | 샘플 기반 모방 | 구조화된 문체 프로필 + 사용자 승인 학습 |
| 부족한 내용 처리 | 주어진 텍스트 안에서 편집 | 필요한 경험·의견·근거를 먼저 질문 |
| 사실 보존 | 프롬프트 지침 | Claim Locker와 자동 검증 게이트 |
| 설명 가능성 | 제한적 | 문장별 수정 이유와 위험 표시 |
| 결과 후보 | 보통 한 번의 재작성 | 최소 수정 / 내 말투 수정 |
| 검증 | 자체 점검 | Voice·Fidelity·Fact·Naturalness Critic |
| 워터마크 | 제거로 오해될 수 있음 | 제거 미보장, 출처·기여 투명성 중심 |
| 장기 학습 | 없음 또는 제한적 | 승인된 편집만 문체 메모리에 반영 |
| 제품 가치 | 자연스러운 재작성 | 사용자의 저자성 복원 및 반복 편집 자동화 |

## 4.3 방어 가능한 강점

OwnDraft의 방어력은 거대한 모델이나 단순 프롬프트에 있지 않다.

- 한국어 AI 문체 패턴 데이터셋
- 사용자별 승인·거절 편집 데이터
- 사실 보존 검증 파이프라인
- 글 목적별 문체 프로필
- 질문을 통해 사용자 고유 정보를 확보하는 흐름
- 실제 사용자 선호 기반 평가 데이터

## 4.4 오픈소스·지식재산권 사용 원칙

- `blader/humanizer`는 비교 기준과 아이디어 출처로 명시한다.
- 저장소의 프롬프트·표·문구를 통째로 복제해 자체 기술처럼 제출하지 않는다.
- 실제 코드나 문구를 차용하면 저장소의 MIT 라이선스 고지와 저작권 표시를 보존한다.
- 위키피디아 패턴 명칭이나 설명을 직접 가져오는 경우 출처와 적용 라이선스를 확인한다.
- OwnDraft의 한국어 패턴 정의, Claim Locker, 질문 흐름, 검증 게이트, 평가셋은 독자적으로 설계하고 변경 이력을 남긴다.
- 공모전 제출물에는 “Humanizer에서 영감을 받았지만 사실 보존·맥락 질문·승인 학습을 추가한 별도 제품”임을 투명하게 설명한다.

# 6. STAGE 1 — 예선용 단일 스킬 설계

## 6.1 스킬 이름

**OwnDraft — 내 말투로 되돌리는 사실 보존형 글 편집기**

## 6.2 예선에서 해결할 단 하나의 문제

> AI 초안을 사용자의 실제 말투로 다듬는 과정에서, 상투적인 표현을 줄이고 사실과 핵심 주장을 그대로 유지한다.

예선에서는 대시보드, 로그인, 장기 메모리, 외부 문서 연동을 넣지 않는다.

## 6.3 입력

필수 입력:

1. 다듬을 원문
2. 글의 목적
3. 예상 독자

선택 입력:

4. 사용자가 직접 쓴 말투 샘플 1~3개
5. 반드시 유지해야 하는 사실·표현
6. 수정 강도
   - `최소 수정`
   - `내 말투 수정`

## 6.4 입력 예시

```text
[글의 목적]
AI를 공부에 활용한 경험을 블로그에 올리려 함

[독자]
AI를 단순 질문 도구로만 쓰는 대학생

[내 말투 샘플]
나는 계획을 세울 때 AI한테 바로 답을 달라고 하기보다,
내가 놓친 부분이 있는지 먼저 질문해 달라고 하는 편이다.
처음에는 귀찮아 보여도 이 과정을 거치면 나중에 계획을 다시 뜯어고칠 일이 줄어든다.

[반드시 유지]
- 회의록 정리 시간이 40분에서 5분으로 줄었다.
- 사용한 도구 이름은 Solar다.

[수정 강도]
내 말투 수정

[원문]
빠르게 변화하는 디지털 시대에 AI는 단순한 도구를 넘어
우리의 업무 방식을 혁신하는 핵심 파트너로 자리 잡고 있습니다...
```

## 6.5 출력

스킬은 다음 순서로 응답한다.

### A. 진단 요약

- 발견한 주요 AI 문체 신호 3~7개
- 사실 확인이 필요한 부분
- 사용자 경험이 부족한 부분

### B. 필요한 질문

재작성 품질을 크게 높일 수 있고 답이 원문에 없을 때만 최대 3개 질문한다.

질문 없이도 안전하게 편집할 수 있으면 바로 수정한다.

### C. 수정본

- 사실과 핵심 주장을 유지
- 사용자 말투 반영
- 글의 목적과 독자에 맞게 편집
- 새 사실을 만들지 않음

### D. 변경 이유

가장 큰 수정 3~7개만 짧게 설명한다.

### E. 사실 보존 결과

```text
이름·기관: 모두 유지
숫자·날짜: 모두 유지
출처·인용: 새로 추가하지 않음
삭제되거나 의미가 바뀐 핵심 주장: 없음
```

## 6.6 내부 처리 순서

```text
1. 입력 형식과 목적 확인
2. 원문에서 사실·주장·경험 추출
3. 잠금 대상 생성
4. 한국어 AI 문체 패턴 진단
5. 말투 샘플 분석
6. 필요한 맥락이 없으면 최대 3개 질문
7. 재작성 계획 생성
8. 수정본 작성
9. 원문과 수정본의 사실·의미 비교
10. 문제 발견 시 한 번만 자체 수정
11. 진단·수정본·변경 이유·보존 결과 출력
```

## 6.7 예선용 기능 경계

### 반드시 포함

- 한국어 AI 문체 신호 탐지
- 선택적 말투 샘플 반영
- 숫자·날짜·이름·출처 보존
- 필요한 경우 맥락 질문
- 수정 이유 설명
- 최소 수정 / 내 말투 수정

### 포함하지 않음

- 계정별 장기 문체 메모리
- 여러 후보를 동시에 생성하는 기능
- Google Docs·Notion 연동
- 탐지기 점수 비교
- 워터마크 제거 판정
- 팀 브랜드 보이스
- 실시간 공동 편집
- 복잡한 에이전트 대시보드

## 6.8 예선 심사에서 보여줄 포인트

1. 입력이 명확하다.
2. 출력이 명확하다.
3. 반복적으로 발생하는 실제 불편을 해결한다.
4. 일반 프롬프트와 달리 사실 보존 검증 과정이 있다.
5. 질문을 통해 사용자의 실제 기여를 늘린다.
6. 한국어에 특화되어 있다.
7. “탐지 우회”가 아니라 “저자성 복원”이라는 사회적 가치가 있다.

# 7. 한국어 AI 글쓰기 신호 체계

초기 버전은 기존 35개 패턴을 참고하되, 한국어에서 자주 보이는 패턴을 별도 규칙으로 관리한다. 모든 패턴은 무조건 삭제하는 규칙이 아니라 **진단 신호**다.

## 7.1 내용 패턴

1. **시대 배경으로 시작**
   - “빠르게 변화하는 현대 사회에서”
2. **중요성 과장**
   - “매우 중요한 역할을 하고 있다”
3. **근거 없는 미래 전망**
   - “앞으로 더욱 발전할 것으로 기대된다”
4. **추상적인 긍정 효과**
   - “다양한 측면에서 긍정적인 영향을 준다”
5. **홍보 문구처럼 과장**
   - “혁신적이고 획기적인 솔루션”
6. **모호한 출처**
   - “전문가들에 따르면”
7. **가짜 균형**
   - “장점도 있지만 한계도 존재한다”
8. **내용 없는 시사점**
   - “우리에게 중요한 시사점을 제공한다”
9. **결론에서 본문 반복**
   - 앞 내용을 그대로 다시 말함
10. **메타 설명**
   - “본 글에서는 세 가지 측면을 살펴본다”
11. **구체성 없는 문제 제기**
   - “여러 문제점이 존재한다”
12. **근거 없이 사회 전체로 확대**
   - 개인 사례를 “우리 사회 전체”의 변화로 과장

## 7.2 구조 패턴

13. **기계적인 세 가지 나열**
14. **모든 문단이 같은 길이**
15. **매 문단이 주장–설명–요약으로 동일**
16. **과도한 소제목**
17. **불필요한 첫째·둘째·셋째**
18. **문장 길이가 지나치게 균일**
19. **질문형 서론 뒤 정답형 설명**
20. **장점–단점–결론 템플릿 반복**
21. **모든 항목을 같은 문법 구조로 맞춤**
22. **짧은 글에도 거대한 결론 문단 추가**

## 7.3 표현 패턴

23. **“단순한 X를 넘어 Y”**
24. **“이러한”, “이를 통해”, “나아가” 반복**
25. **“~할 수 있습니다” 종결 반복**
26. **“~에 있어”, “~의 측면에서” 남용**
27. **명사화 과다**
   - “효율성 향상에 대한 필요성의 증대”
28. **수동·피동 표현 과다**
29. **영어 번역투**
30. **긴 대시·콜론 남용**
31. **형용사 세 개 나열**
   - “빠르고, 편리하고, 강력한”
32. **불필요한 완곡 표현**
   - 핵심 판단을 끝까지 흐림
33. **“결론적으로”, “종합하면” 자동 마무리**
34. **“중요한 역할”, “새로운 가능성” 반복**
35. **“X가 아니다. 바로 Y다.” 과장 대조**
36. **“깊이 들여다보면” 같은 가짜 깊이 표현**
37. **“효과적으로”, “체계적으로” 같은 빈 부사**
38. **과도한 볼드체·이모지·장식**
39. **챗봇식 인사와 마무리**
   - “도움이 되었기를 바랍니다”
40. **사용자가 쓰지 않는 지나친 존칭·격식**

## 7.4 문맥에 따라 유지해야 하는 경우

- 보고서에서 번호 나열이 실제 구조를 명확하게 만드는 경우
- 법률·정책 문서에서 일정한 형식이 필요한 경우
- 사용자가 원래 긴 문장을 자주 사용하는 경우
- 브랜드 문체가 의도적으로 격식 있는 경우
- 출처를 명시한 전망이나 평가인 경우

패턴 수를 줄이는 것이 목표가 아니다. 글의 목적과 사용자 문체에 맞지 않는 패턴만 수정한다.

# 8. 사실 보존 설계 — Claim Locker

## 8.1 목적

문체를 바꾸는 과정에서 발생할 수 있는 가장 큰 실패는 글이 자연스러워지는 대신 사실이 달라지는 것이다.

Claim Locker는 재작성 전에 변경 위험이 있는 정보를 구조화하고 잠근다.

## 8.2 추출 대상

- 사람 이름
- 회사·기관·제품명
- 날짜·시간
- 숫자·단위·금액·비율
- 인용문
- 링크·출처
- 사건의 순서
- 사용자 개인 경험
- 확정된 의견
- 추정·가설
- 부정 표현
- 조건과 예외

## 8.3 Claim 예시

```json
{
  "claim_id": "clm_0014",
  "source_text": "회의록 정리에 40분이 걸렸지만 지금은 5분이면 끝난다.",
  "claim_type": "personal_experience",
  "entities": [],
  "numbers": [
    {"value": 40, "unit": "분"},
    {"value": 5, "unit": "분"}
  ],
  "polarity": "positive_change",
  "editable": false,
  "evidence_type": "user_statement",
  "status": "locked"
}
```

## 8.4 검증 규칙

- 잠긴 숫자는 값과 단위를 모두 보존한다.
- 이름과 기관은 임의로 줄이거나 바꾸지 않는다.
- 직접 인용은 문장부호를 제외하고 내용을 바꾸지 않는다.
- 추정은 확정 표현으로 바꾸지 않는다.
- “아니다”, “없다” 같은 부정 의미를 뒤집지 않는다.
- 새 통계와 출처를 추가하지 않는다.
- 삭제한 주장이 있으면 결과에 표시한다.
- 의미가 애매하면 사용자에게 확인한다.

## 8.5 실패 시 처리

- 사실 검증이 실패하면 수정본을 바로 출력하지 않는다.
- 한 차례 자동 수정을 시도한다.
- 다시 실패하면 문제 문장을 표시하고 원문 유지 또는 사용자 확인을 요청한다.

# 9. 문체 프로필 설계

## 9.1 원칙

문체는 단순히 자주 쓰는 단어 몇 개가 아니다.

- 문장 길이
- 문단 호흡
- 결론을 먼저 말하는지
- 예시를 언제 드는지
- 단정과 완곡의 정도
- 존댓말·반말
- 괄호·쉼표·줄바꿈 습관
- 유머의 방식
- 설명의 순서
- 어떤 표현을 싫어하는지

이를 사람이 확인할 수 있는 구조화된 프로필로 만든다.

## 9.2 Voice Profile 예시

```yaml
profile_version: 1
language: ko
formality:
  level: semi_casual
  honorific: mixed
sentence:
  average_length: short
  variance: high
  preferred_opening: conclusion_first
paragraph:
  average_sentences: 3
  spacing: frequent
reasoning:
  order:
    - conclusion
    - reason
    - concrete_example
  uncertainty_style:
    - "~인 것 같다"
    - "~라고 봄"
punctuation:
  comma_frequency: low
  parentheses_frequency: medium
  em_dash: avoid
lexicon:
  preferred:
    - "일단"
    - "그냥"
    - "결국"
  avoided:
    - "빠르게 변화하는 시대"
    - "단순한 도구를 넘어"
    - "결론적으로"
rhetoric:
  list_preference: flexible
  metaphor_frequency: low
  humor_style: dry
```

## 9.3 학습 데이터 정책

- 예선: 현재 대화에 제공한 샘플만 일시적으로 사용한다.
- 결선: 사용자가 명시적으로 저장한 샘플만 장기 보관한다.
- 생성된 결과를 자동으로 학습하지 않는다.
- 사용자가 수락한 수정과 직접 수정한 문장만 학습 후보로 사용한다.
- 사용자는 문체 프로필을 확인·수정·삭제할 수 있다.
- 사용 목적별로 프로필을 분리한다.
  - 블로그
  - 업무 메일
  - 보고서
  - SNS

## 9.4 과적합 방지

- 샘플이 짧으면 확신도를 낮게 표시한다.
- 표면적인 말버릇만 과도하게 반복하지 않는다.
- 특정 표현이 샘플에 한 번 나왔다고 핵심 습관으로 확정하지 않는다.
- 새 글의 목적이 기존 샘플과 다르면 문체와 장르 규칙을 분리한다.

# 10. 맥락 질문 설계 — Context Interview

## 10.1 질문이 필요한 이유

가장 자연스러운 글은 단어만 바꾼 글이 아니라, 사용자만 제공할 수 있는 구체적인 정보가 들어간 글이다.

OwnDraft는 다음 경우에 질문한다.

- 추상적인 주장만 있고 실제 사례가 없음
- “효율이 좋아졌다”지만 무엇이 얼마나 좋아졌는지 없음
- 사용자의 입장이 모호함
- 글의 핵심 결론이 없음
- 독자에게 어떤 행동을 기대하는지 없음
- 사실과 의견을 구분하기 어려움

## 10.2 질문 규칙

- 최대 3개
- 한 질문에는 한 가지 정보만 요청
- 답하기 쉽게 구체적으로 질문
- 이미 원문에 있는 내용을 다시 묻지 않음
- 질문 없이도 안전하게 수정할 수 있으면 질문하지 않음
- 사용자가 건너뛰면 사실을 만들지 않고 보수적으로 편집

## 10.3 좋은 질문 예시

- “AI를 쓰기 전과 후에 실제로 줄어든 작업 시간이 있나요?”
- “이 글을 읽은 사람이 마지막에 무엇을 해보길 바라나요?”
- “‘불편했다’고 느낀 가장 구체적인 순간을 한 가지 말해 주세요.”
- “이 내용은 직접 경험인가요, 다른 자료에서 본 내용인가요?”

## 10.4 나쁜 질문 예시

- “더 구체적으로 말해 주세요.”
- “어떤 느낌이었나요?”
- 한 번에 경험·수치·감정·결론을 모두 묻는 질문
- 이미 입력된 독자와 목적을 다시 묻는 질문

# 11. STAGE 2 — 결선용 서비스 MVP

## 11.1 결선 MVP의 한 줄 정의

> 개인 문체를 저장하고, AI 초안을 질문–재작성–검증–승인 과정을 통해 실제 사용자의 글로 편집하는 웹 서비스

## 11.2 사용자 화면

### 화면 A — 온보딩과 문체 프로필

- 사용 목적 선택
- 직접 쓴 글 3개 이상 등록
- 자동 생성된 문체 프로필 확인
- 잘못 분석된 특징 수정
- 금지 표현과 선호 표현 직접 지정

### 화면 B — 편집 워크스페이스

- 왼쪽: 원문
- 오른쪽: 수정본
- 상단: 목적, 독자, 수정 강도
- 하단: 필요한 맥락 질문
- 문장별 상태:
  - 유지
  - 표현 수정
  - 삭제 추천
  - 사실 확인 필요
  - 사용자 경험 필요

### 화면 C — 변경 근거

문장을 선택하면 다음을 표시한다.

- 원문
- 수정문
- 발견 패턴
- 수정 이유
- 보존된 사실
- 위험도

### 화면 D — 승인과 학습

문장별 행동:

- 수락
- 거절
- 직접 수정
- 다시 제안

사용자가 수락하거나 직접 수정한 결과만 문체 메모리 학습 후보가 된다.

### 화면 E — 품질 보고서

- 잠긴 사실 유지 여부
- 새 사실 추가 여부
- AI 상투 패턴 변화
- 문체 프로필 일치 항목
- 사용자 제공 내용과 AI가 편집한 범위
- 검토가 필요한 문장

“AI 작성 확률 17%” 같은 불확실한 단일 점수는 제공하지 않는다.

# 12. 결선 MVP 아키텍처

## 12.1 설계 원칙

- 여러 자율 에이전트를 과도하게 늘리지 않는다.
- 각 에이전트는 명확한 한 가지 책임을 가진 **역할 기반 처리 단계**다.
- 전체 흐름은 예측 가능한 상태 머신으로 관리한다.
- 구조화된 JSON 입출력을 사용한다.
- 검증 단계는 생성 단계와 분리한다.
- 재시도는 최대 한 번으로 제한한다.
- 초기에는 한 문서 단위 동기 처리로 충분하다.

## 12.2 권장 기술 구성

### Frontend

- Next.js + TypeScript
- 문서 입력 및 Diff 편집기
- 문장별 승인 UI
- 프로필 관리 화면

### Backend

- FastAPI + Python 3.12
- Pydantic 기반 요청·응답 모델
- 역할별 LLM 호출 오케스트레이션
- 비동기 병렬 Critic 실행
- 정책·검증 게이트

### Data

- PostgreSQL
- `pgvector` 또는 동등한 벡터 검색 기능
- 문체 샘플, 프로필, 문서 버전, 승인 로그 저장
- Redis는 결선 MVP에서 꼭 필요할 때만 도입

### Model

- 대회 환경에서는 Solar LLM을 중심으로 구성
- 구조화 출력과 재작성에 동일 모델을 사용할 수 있음

# 13. 역할별 에이전트 명세

## 13.1 Intake Validator

책임:

- 입력 누락 확인
- 글 목적·독자·언어 확인
- 지나치게 긴 문서 분할
- 코드, 표, 링크, 인용 구간 보호
- 요청이 탐지 우회나 워터마크 제거만을 목표로 하는지 확인

출력:

```json
{
  "language": "ko",
  "document_type": "blog_post",
  "audience": "college_students",
  "edit_mode": "voice",
  "protected_spans": [],
  "requires_policy_redirect": false
}
```

## 13.2 Claim Locker

책임:

- 사실·주장·경험 추출
- 변경 가능 여부 지정
- 원문 위치 저장
- 검증용 Fact Ledger 생성

## 13.3 Pattern Scanner

책임:

- 기존 35개 패턴과 한국어 전용 패턴 탐지
- 문장별 패턴, 심각도, 근거 기록
- 문맥상 유지해야 할 가능성 표시

출력 예시:

```json
{
  "span_id": "s_12",
  "pattern": "abstract_positive_effect",
  "severity": "medium",
  "reason": "효과가 무엇인지 구체적인 대상이나 결과가 없음",
  "action": "ask_or_rewrite"
}
```

## 13.4 Voice Profiler

책임:

- 현재 목적과 맞는 문체 샘플 선택
- 구조화된 문체 프로필 생성·갱신
- 샘플 부족 시 확신도 표시
- 표면 표현과 구조적 습관을 분리

## 13.5 Context Gap Analyzer

책임:

- 좋은 재작성에 필요한 정보 중 원문에 없는 것 확인
- 질문 가치가 높은 항목 순위화
- 최대 3개 질문 생성
- 질문 없이 진행할 수 있는지 판단

## 13.6 Rewrite Planner

책임:

- 문장별로 `유지`, `삭제`, `축약`, `재작성`, `질문 반영`, `순서 변경` 결정
- 사실 잠금과 문체 프로필을 동시에 반영
- Writer가 임의로 구조를 바꾸지 않도록 계획 제공

출력 예시:

```json
{
  "paragraph_id": "p_03",
  "goal": "추상적인 장점을 실제 경험으로 교체",
  "operations": [
    {"span_id": "s_12", "action": "delete"},
    {"source": "user_answer_01", "action": "insert_after", "target": "s_11"}
  ],
  "locked_claims": ["clm_0014"]
}
```

## 13.7 Candidate Writer

책임:

- 계획을 따라 수정본 생성
- 새 사실 금지
- 선택한 수정 강도 준수
- 코드·링크·인용·서식 보호

초기 MVP는 후보 1개만 생성한다. 사용자가 다시 제안을 요청할 때만 대체 후보를 만든다.

## 13.8 Fact Critic

검사:

- 잠긴 수치·이름·날짜·출처 보존
- 부정 의미 유지
- 새 사실 추가 여부
- 인용 왜곡 여부

## 13.9 Fidelity Critic

검사:

- 핵심 주장 보존
- 논리 관계 유지
- 조건과 예외 유지
- 문단 순서 변경으로 의미가 왜곡되지 않았는지

## 13.10 Voice Critic

검사:

- 문체 프로필과 결과의 일치
- 말버릇 과복제 여부
- 글 목적과 문체의 충돌 여부
- 샘플에 없는 특징을 임의로 추가했는지

## 13.11 Naturalness Critic

검사:

- 한국어 어순
- 반복되는 연결어와 종결어미
- 번역투
- 불필요한 장식
- 문장 호흡의 지나친 균일성
- 억지 구어체

## 13.12 Acceptance Gate

통과 조건:

- 잠긴 사실 오류 0개
- 새 사실 0개
- 심각한 의미 왜곡 0개
- 높은 심각도의 미해결 패턴이 허용 기준 이하
- 문체 프로필의 핵심 제약 위반 없음

실패 시:

- Writer에 검증 오류만 전달해 한 번 수정
- 두 번째 실패 시 사용자에게 문제 구간 표시

# 16. 워터마크와 출처 정책

## 16.1 기술적 전제

Claude와 SynthID Text는 숨은 문자를 삽입하는 방식이 아니라 생성 시 단어·토큰 선택에 통계적인 패턴을 남기는 방식이다.

따라서 다음은 모델 텍스트 워터마크 제거가 아니다.

- 제로폭 문자 삭제
- 메모장에 붙여넣기
- HTML 태그 제거
- 파일 메타데이터 제거
- 문장부호 정리

이 기능들은 필요하면 `문서 위생 검사`로 제공할 수 있지만, 워터마크 제거라고 부르지 않는다.

## 16.2 제품 표시 원칙

제공 가능:

- 사용자가 알려준 초안 생성 도구 기록
- 사용자가 추가한 사실·경험 표시
- AI가 편집한 구간 표시
- 공식 탐지 API가 실제 공개되고 이용 가능한 경우의 선택적 연결
- 불확실성을 포함한 출처 설명

제공하지 않음:

- “워터마크 제거 완료”
- “AI 탐지 불가능”
- “Claude 관여 확률 0%”
- “Turnitin 통과 보장”
- 비공식 탐지기 점수를 진실처럼 표시

## 16.3 Contribution Map

출처 투명성을 위해 문서의 기여 범위를 다음처럼 보여준다.

```text
사용자가 직접 제공한 사실: 7개
사용자가 직접 제공한 경험: 2개
사용자가 직접 제공한 판단: 4개
AI가 새로 추가한 사실: 0개
AI가 표현을 재구성한 문장: 11개
사용자가 최종 승인한 문장: 9개
추가 검토가 필요한 문장: 1개
```

이것은 저자 판정 점수가 아니라 편집 과정 기록이다.

# 17. 안전·오용 방지

## 17.1 탐지 우회 요청

사용자가 “AI 탐지 0%”, “워터마크 삭제”, “교수에게 안 걸리게”를 명시적으로 요청하면:

1. 우회나 제거를 보장하지 않는다고 알린다.
2. 글의 사실성·개인 경험·문체를 개선하는 편집으로 전환한다.
3. 평가 과제라면 사용자가 직접 제공한 주장과 근거를 중심으로 돕는다.
4. 탐지기 점수를 최적화 목표로 사용하지 않는다.

## 17.2 타인 문체 모방

- 살아 있는 작가·유명인·특정 개인의 고유 문체를 그대로 복제하지 않는다.
- 대신 “짧은 문장”, “건조한 유머”, “결론 우선” 같은 일반적 특성으로 변환한다.
- 팀·브랜드 문체는 권한이 있는 사용자만 등록한다.

## 17.3 사실과 출처

- 출처가 필요한 주장은 사용자가 제공하지 않으면 삭제·완화·질문한다.
- 인용문을 만들어내지 않는다.
- 불확실한 내용은 확정적으로 쓰지 않는다.
- 의료·법률·금융 등 고위험 문서는 별도 경고와 강화 검증이 필요하며 초기 MVP 범위에서는 제한한다.

## 17.4 개인정보

- 문체 샘플은 개인 식별 가능성이 있는 데이터로 취급한다.
- 기본 비공개
- 제3자 공유 없음
- 삭제와 내보내기 지원
- 운영자도 원문을 볼 필요가 없도록 설계

# 18. 평가 프레임워크

OwnDraft는 AI 탐지기 점수가 아니라 다음 지표로 평가한다.

## 18.1 자동 평가

### 1. Locked Fact Preservation

- 이름·숫자·날짜·기관·인용 보존율
- 목표: 심각 오류 0개

### 2. New Claim Rate

- 원문이나 사용자 답변에 없는 새 사실 비율
- 목표: 0%

### 3. Semantic Fidelity

- 핵심 주장, 조건, 부정, 인과 관계 보존
- LLM judge와 사람이 함께 평가
- 목표: 평균 4.5/5 이상

### 4. Pattern Reduction

- 문맥상 부적절한 AI 패턴 감소율
- 목표: 60% 이상
- 모든 패턴 제거가 목표는 아님

### 5. Voice Constraint Match

- 문장 길이, 종결어미, 문단 구조, 금지 표현 준수
- 목표: 핵심 제약 90% 이상 충족

### 6. Latency and Cost

- 예선: 사용자가 체감 가능한 시간 안에 응답
- 결선: 단계별 지연을 기록하고 병렬 검증
- 구체 목표는 실제 Solar API 측정 후 확정

## 18.2 사용자 평가

### 1. 사용자 선호도

질문:

> “일반 AI 재작성과 OwnDraft 결과 중 어느 쪽이 실제 내가 쓴 글에 더 가까운가?”

목표: OwnDraft 승률 65% 이상

### 2. 문장 수락률

- 제안 문장 중 수락 또는 소폭 수정 후 수락된 비율
- 목표: 70% 이상

### 3. 재수정량

- 최종 발행 전 사용자가 다시 바꾼 문자 수
- 일반 Humanizer 대비 감소

### 4. 구체성 향상

- 실제 사례, 수치, 판단이 추가되었는가
- 단, 사용자가 직접 제공한 정보만 인정

## 18.3 비교 실험

네 가지 결과를 비교한다.

1. 원래 AI 초안
2. 일반적인 “자연스럽게 바꿔줘” 프롬프트
3. 오픈소스 Humanizer 방식
4. OwnDraft

평가자는 결과의 출처를 모르는 상태에서 다음을 평가한다.

- 자연스러움
- 사용자다움
- 의미 보존
- 구체성
- 신뢰성
- 발행 의향

## 18.4 예선용 테스트셋

최소 20개:

- 블로그 5개
- 업무 메일 5개
- 보고서·과제 설명 5개
- SNS·소개 글 5개

각 샘플에 다음을 수동 표시한다.

- 잠긴 사실
- 핵심 주장
- 발견할 패턴
- 허용 가능한 수정
- 금지되는 수정

```text
내가 AI를 가장 유용하게 느낀 순간은 거창한 작업을 했을 때가 아니다.
회의가 끝날 때마다 40분씩 걸리던 회의록 정리가 지금은 5분이면 끝난다.
적어도 나한테 AI의 가치는 ‘혁신’ 같은 말보다 이런 반복 작업을 줄여주는 데 있다.
```

## 19.6 데모에서 보여줄 검증

```text
40분: 유지
5분: 유지
새 통계: 없음
새 출처: 없음
사용자 경험 반영: 1개
AI 상투 패턴: 6개 → 0개
```

이 데모는 단순한 문장 치환이 아니라, 질문을 통해 사용자의 실제 내용을 글에 복원했다는 점을 보여준다.

# 25. 심사위원에게 전달할 핵심 메시지

## 문제

AI로 초안을 만드는 시간은 줄었지만, 사용자는 매번 AI 같은 표현을 지우고 자신의 경험과 말투를 다시 넣어야 한다.

## 해결

OwnDraft는 AI 초안을 바로 바꾸지 않는다. 먼저 사실을 잠그고, 사용자의 문체를 분석하고, 부족한 개인 경험을 질문한 뒤, 의미를 검증하며 편집한다.

## 에이전트가 필요한 이유

- 글의 목적을 파악한다.
- 사실과 표현을 분리한다.
- 부족한 정보를 능동적으로 질문한다.
- 재작성 계획을 세운다.
- 여러 기준으로 결과를 검증한다.
- 사용자 승인 결과를 다음 편집에 반영한다.

## 사회적 가치

OwnDraft는 AI 사용을 숨기는 서비스가 아니다. 사용자가 실제로 생각하고 경험한 내용을 글에 더 많이 반영하고, AI가 개입한 범위와 변경 이유를 투명하게 보여주는 서비스다.

## 한 줄 피치

> **AI 초안을 감추는 것이 아니라, 그 안에 사라진 내 생각과 내 말투를 되찾아주는 글쓰기 편집 에이전트.**

# 28. 최종 결정 요약

OwnDraft는 다음 세 축으로 개발한다.

1. **Pattern Intelligence**
   - 한국어 AI 문체 신호를 문맥에 맞게 진단한다.

2. **Authorship Restoration**
   - 사용자의 실제 경험과 문체를 질문·프로필을 통해 글에 복원한다.

3. **Claim Integrity**
   - 사실, 숫자, 이름, 출처, 핵심 주장을 잠그고 재작성 후 검증한다.

예선에서는 이 세 축을 한 번의 대화형 스킬로 압축한다. 결선에서는 개인 문체 메모리, Diff 편집기, 문장별 승인, 품질 보고서를 갖춘 서비스로 확장한다.

**제품의 성공 기준은 AI 탐지 점수를 낮추는 것이 아니다. 사용자가 “이건 진짜 내가 쓴 글 같다”고 느끼면서도, 사실과 의미가 그대로 유지되는 것이다.**
